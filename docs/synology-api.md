Рабочие заметки проекта. Здесь только выводы и проверенные факты — текст
официальной документации Synology проприетарный, копировать его сюда нельзя.

Всё в этом файле проверено на живом NAS: **DSM 7.2.2**, Download Station
**4.1.2-5012**, File Station **1.4.4-2221**. Где поведение расходится с
документацией или её вовсе нет — отмечено явно.

## Общие правила вызовов

- Путь и допустимые версии каждого API узнаются в рантайме через `SYNO.API.Info`:
  они отличаются между DSM 6 и 7 и между моделями NAS.
- У API с `requestFormat: "JSON"` **каждое значение параметра** кодируется как
  JSON: строка `url` уходит как `"url"`, в кавычках. Иначе DSM отвечает 101 или
  105 без объяснений. Официальный пример это подтверждает: `folder_path=%22%2Fvideo%22`.
- Ошибки приходят в теле ответа с HTTP 200. На коды статуса полагаться нельзя.
- Сессия молча протухает — нужен прозрачный повторный вход по кодам 105, 106, 107, 119.

## Ловушка №1: успешный ответ на неудавшееся действие

Самое опасное место во всём API. `pause`, `resume` и `delete` отвечают
**в трёх разных формах**, и в двух из них провал приходит под `success: true`:

| Вызов | `success` | Где лежит отказ |
|---|---|---|
| `DownloadStation2.Task` `pause` | `false` | `error.errors.failed_task[]` |
| `DownloadStation2.Task` `resume` / `delete` | **`true`** | `data.failed_task[]` — объект |
| `DownloadStation.Task` `delete` (легаси) | **`true`** | `data[]` — голый массив |
| `DownloadStation.Task` `pause` (легаси) | `false` | `error.code: 101`, без массива |

Пример ответа, который легко принять за успех:

```json
{"data": {"failed_task": [{"error": 544, "id": "dbid_999999"}]}, "success": true}
```

Не разобрать массив — значит показать пользователю «снято с паузы» там, где NAS
ничего не сделал. В проекте это разбирает `actionResult.UnmarshalJSON`
в `internal/dsm/downloadstation/station.go`.

## Ловушка №2: `limit = -1` роняет File Station

В Download Station `limit: -1` — штатный способ получить все задачи разом.
В File Station такой же запрос **валит обработчик в HTTP 502** — и `list`, и
`list_share`, на любой версии API:

```
v1, limit=50  → 11 файлов      v1, limit=-1  → HTTP 502
v2, limit=50  → 11 файлов      v2, limit=-1  → HTTP 502
```

Поэтому списки File Station читаются страницами по `total` из ответа, а
`limit: -1` не передаётся никогда.

Ошибка выглядит как сломанная версия API: если сравнивать запросы, у которых
различается и версия, и `limit`, легко заключить, что «версия 2 не работает».
Версия здесь ни при чём.

Фолбэк по версиям в проекте всё равно оставлен (`Client.CallVersioned`): он
дёшев, а коды 103 и 104 на разных сборках DSM встречаются.

## Пути: ведущий слеш обязателен не везде

| | Формат |
|---|---|
| File Station (`folder_path`, `path`) | `/Media/Music` — с ведущим слешем |
| Download Station (`destination`) | `Media/Music` — **без** ведущего слеша, иначе 403 |

## Загрузка файлов (multipart)

`SYNO.FileStation.Upload` работает по RFC 1867, и здесь правила другие:

- Каждый параметр идёт **отдельной частью** формы, а не в строке запроса.
- Значения передаются **как есть, без JSON-кавычек** — в отличие от обычных
  вызовов того же API.
- Бинарные данные обязаны быть **последней** частью, иначе ошибка 1800.
- `overwrite` нужно задавать явно: без него DSM отвечает ошибкой, когда файл
  с таким именем уже есть.
- **`_sid` передаётся в строке запроса, а не частью формы.** Из тела multipart
  DSM его не читает и отвечает 119 «SID не найден» — при том, что тот же SID
  в обычных вызовах работает. Признак именно этой ошибки: повторный вход
  ничего не меняет, 119 приходит снова.

## Download Station: создание задачи

Поколения расходятся в том, что обязательно:

| | `DownloadStation2.Task` (v2) | `DownloadStation.Task` (легаси) |
|---|---|---|
| ссылки | `url` — массив | `uri` — строка через запятую |
| папка | `destination` **обязателен** | `destination` необязателен |
| формат пути | `Media/TV Shows`, без ведущего слеша | так же |
| прочее | `create_list: false` обязателен | — |

- Без `destination` версия 2 отвечает `{"code": 120, "errors": {"name": "destination", "reason": "required"}}`
  даже когда папка по умолчанию задана в настройках пакета.
- Ведущий слеш (`/Media/TV Shows`) отвергается кодом 403.
- Добавочные кавычки вокруг пути — тоже 403. Обычная строка, кодировщик JSON
  сам добавит свои.
- `create_list: true` задачу **не создаёт** — это режим предварительного выбора файлов.
- Ссылка на `.torrent`: v2 распознаёт её и сразу заводит `bt`-задачу, легаси
  сначала качает сам файл как `https`-задачу.

## Различия полей между поколениями

На них ломается перенос кода с одного API на другое:

| | v2 | легаси |
|---|---|---|
| список задач | поле `task` | поле `tasks` |
| статус | число (`5` = finished) | строка (`"finished"`) |
| время создания | `created_time` | `create_time` |
| пароль архива | `extract_password` | `unzip_password` |
| время раздачи | `seed_elapsed` | `seedelapsed` |
| id в действиях | массив | строка через запятую |
| сведения о томах | `Settings.Global` | отсутствуют |

## Коды ошибок

Коды 400–408 Download Station совпадают с официальной таблицей: 400 — загрузка
файла не удалась, 401 — предел числа задач, 402 — папка недоступна, 403 — папки
нет, 404 — нет такой задачи, 405 — недопустимое действие, 406 — нет папки по
умолчанию, 407 — не удалось задать папку, 408 — файла нет.

**Кода 544 в документации нет**, но он приходит, когда действие адресовано
несуществующей задаче.

Коды входа: 400 — неверный пароль, 403 — требуется код 2FA, 404 — неверный код 2FA.
Для сервиса это значит: заводить отдельного пользователя **без** двухэтапной проверки.

## File Station: операции

- **Удаление** — два пути: `Delete` `version=1` `method=delete` синхронно, либо
  `version=2` `method=start` → возвращает `taskid`, затем `status` и `stop`.
  Для больших папок нужен второй.
- **Переименование** — `Rename` `method=rename`, где `path` и `name` — **массивы**,
  даже для одного файла.
- Учитывая ловушку №2, обе операции нужно пробовать с понижением версии.

## Постановка задачи файлом `.torrent`

Работает через тот же multipart, но кодирование полей — **третий вариант**,
не совпадающий ни с обычными вызовами, ни с загрузкой в File Station:

| Куда | Значения полей формы |
|---|---|
| `DownloadStation2.Task` `create` | **как JSON**: `"file"`, `["torrent"]`, `"Media/TV Shows"` |
| `FileStation.Upload` | **без кавычек**: `/Media/Music`, `false` |

Рабочий набор для DS2: `type` = `"file"`, `file` = `["torrent"]`,
`create_list` = `false`, `destination` в кавычках, а часть с бинарными данными
называется так же, как элемент в списке `file` — `torrent`. Ответ содержит
`task_id`.

Задача сразу заводится как `bt`, в отличие от постановки по ссылке на тот же
`.torrent`, где NAS сначала качает сам файл.

**Легаси-путь загрузки файла на DSM 7 не работает:** `SYNO.DownloadStation.Task`
`create` с частью `file` отвечает 101 на всех своих версиях (1, 2 и 3). Судя по
всему, его заменил DownloadStation2. Ветка в коде оставлена для DSM 6, но там
не проверена.

## Файлы, трекеры и пиры задачи — только пока она активна

`SYNO.DownloadStation2.Task.BT.File`, `.BT.Tracker` и `.BT.Peer` отвечают
**кодом 1913** для завершённых и приостановленных задач, независимо от версии
API и формы параметров. Как только задача действительно качается (статус 2)
или раздаётся, те же вызовы отдают данные.

Код 1913 в документации отсутствует; на ошибку в параметрах он не указывает —
имя `task_id` проверяется отдельно и при его отсутствии приходит код 120
`{name: task_id, reason: required}`.

Форма ответа `BT.File.list`:

```json
{"items": [{"index": 0, "name": "ubuntu-24.04.5-live-server-amd64.iso",
            "priority": "normal", "size": 4080486400,
            "size_downloaded": 0, "wanted": true}],
 "limit": 10, "offset": 0, "total": 1}
```

Приоритет файла — строка, а не число. `wanted` показывает, качается ли файл
вообще. Менять и то и другое умеет метод `set` того же API.

Практический вывод для интерфейса: список файлов у докачанной задачи получить
нельзя, и это нормальное поведение NAS, а не сбой — экран должен говорить об
этом прямо, а не показывать пустоту.

## Приоритет задачи — это про eMule, а не про торренты

`SYNO.DownloadStation2.Task` `edit` принимает `priority` («low», «normal»,
«high», «auto») и отвечает успехом, но для BT-задачи значение **не
сохраняется и никогда не возвращается**: ни `list`, ни `get` с любым
`additional` не отдают поле `priority` в `detail`.

Причина видна в коде самой веб-морды Download Station
(`/var/packages/DownloadStation/target/ui/download.js` на NAS):

```js
b.priority = SYNO.SDS.DownloadStation.aMule.Utils.getPriorityDS(
    a.additional.detail.priority)
```

Приоритет обрабатывается модулем **aMule**, то есть относится к задачам
eMule. У торрентов его нет, поэтому поле всегда пустое, а колонка приоритета
в интерфейсе DSM по умолчанию скрыта (`hidden: true`).

Вывод: для BT такого переключателя строить нельзя — вызов принимается, но
ничего не делает. Приоритет **файлов внутри раздачи** — отдельная, рабочая
возможность (`Task.BT.File` `set`).

Полезное попутно: интерфейс читает подробности методом **`get`** с
параметром `id` (список) и `additional: ["detail"]`, а не `list`.

## Копирование и перенос: завершающий слеш ломает путь

`SYNO.FileStation.CopyMove` асинхронный: `start` отдаёт `taskid`, дальше
`status` до `finished`, при необходимости `stop`. Перенос от копирования
отличает только `remove_src`.

Ловушка: **завершающий слеш в `dest_folder_path` даёт ошибку 1002 с кодом
418 «Illegal name or path»**. Путь `/Download/dst` работает, `/Download/dst/`
— нет.

При `overwrite: false` и совпадении имён операция не падает, а завершается с
`skipstatus`, и файлы молча пропускаются — об этом стоит сообщать
пользователю, иначе он решит, что всё скопировалось.

## Предпросмотр файлов

- `SYNO.FileStation.Thumb` `get` отдаёт миниатюру: `small` заметно меньше
  оригинала, а `medium`, `large` и `original` для небольших картинок
  возвращают исходный файл. Для текста и архивов приходит HTTP 404 — это
  нормально, миниатюры у них нет.
- `SYNO.FileStation.Download` `download` с `mode: "open"` отдаёт содержимое
  с правильным Content-Type (`text/plain`, `image/png`), а с `mode:
  "download"` просит браузер сохранить файл.
- Оба возвращают **не JSON, а байты**, и об ошибке сообщают, подменив тип
  содержимого на `application/json`. Клиент должен смотреть на Content-Type,
  а не пытаться разобрать ответ как JSON.

## Статусы задач: числовая таблица целиком

`SYNO.DownloadStation2.Task` `list` отдаёт статус **числом**, легаси-API —
строкой. Таблица переписана из `getStatusString` в коде самой Download
Station — `/webman/3rdparty/DownloadStation/download.js` на NAS:

| коды | состояние |
|---|---|
| 1, 11, 12 | waiting |
| 2 | downloading |
| 3 | paused |
| 4, 13, 14 | finishing |
| 5 | finished |
| 6 | hash_checking |
| 7 | pre-seeding |
| 8 | seeding |
| 9 | filehosting_waiting |
| 10 | **extracting** |
| 15 | captcha_needed |
| 102…134 | конкретные причины отказа |
| всё остальное | ошибка (`default` в самом интерфейсе DS) |

Отсюда два вывода.

**Ошибка не имеет своего кода в списке.** Упавшая раздача приходит как `101`,
и в `getStatusString` этот код не упомянут — он попадает в `default`. Сверка
на живом NAS это подтвердила: легаси-API на ту же задачу отвечает
`status: "error"` и `status_extra: {"error_detail": "unknown"}`, а
DownloadStation2 — `101` и никакого `status_extra`. Причину отказа словами
знает только легаси-API.

**Наша карта была сдвинута начиная с седьмого кода.** Считалось, что 7 —
seeding, 8 — ожидание, 9 — распаковка, 10 — ошибка. На деле 10 это
**распаковка**, и задача, которую Download Station распаковывала, показывалась
пользователю как упавшая.

Коды 102–134 называют причину: `download_task_disk_full`,
`download_task_dest_deny`, `error_invalid_torrent`, `download_task_timeout`
и так далее. Семь из них показываются пользователю словами — те, что реально
случаются при торрентах и прямых ссылках: нет места, папка недоступна,
ссылка не работает, истекло ожидание, дубль, битый торрент, не распаковалось.
Остальные (нет Python, статья NZB, parchive) относятся к сценариям, которых в
этом приложении нет, и остаются просто «ошибкой»: неверная причина хуже
отсутствия причины.

Причину отдаёт **только DownloadStation2** — по номеру кода. У легаси-API она
приходит строкой в `status_extra.error_detail`, но её словарь нигде не
записан: единственное встреченное вживую значение — `unknown`. Поэтому на
легаси-пути причина не показывается, вместо угадывания.

## Ещё найденное

- `SYNO.DownloadStation.Task` `method=edit` меняет `destination` **уже созданной**
  задачи (с версии 2). Полезно: папку можно исправить, не пересоздавая закачку.
- `SYNO.DownloadStation.BTSearch` ищет по трекерам через модули, настроенные в
  пакете. Даёт сценарий «написал название в бот → выбрал из списка → качается».
- `SYNO.DownloadStation2.Task.List.Polling` существует, но `Task.List` как
  отдельный API методов `list`/`start` не имеет — список задач берётся у
  `SYNO.DownloadStation2.Task` методом `list`.

## Витрина в Центре пакетов

Проверено на живом DSM 7.2.2, потому что ни один пакет SynoCommunity этим не
пользуется — у всех 38 в их каталоге `snapshot` пустой.

- Скриншоты в карточке пакета берутся **только из каталога**, поля `snapshot`
  (массив ссылок). В INFO самого `.spk` поля для скриншотов нет вообще.
- Браузер их не грузит напрямую: `PkgManApp.js` подставляет в `<img src>`
  адрес **`SYNO.Core.Package.Screenshot.Server`** `get` с параметрами `name`,
  `ver`, `link` и `index`, где `index` — хеш имени файла из ссылки. Отдельного
  вызова, который наполняет кэш, в коде интерфейса нет.
- Параметры кодируются как у обычных вызовов — **JSON**: `name`, `ver` и
  `link` в кавычках, `index` числом. С `ver` без кавычек приходит ошибка 120
  `{"name":"ver","reason":"type"}`.
- **Чего добиться не удалось:** отдать произвольную ссылку и получить по ней
  картинку. Ответ `image/png` пришёл ровно один раз — на ссылку иконки,
  которая в тот момент уже была в каталоге, закэшированном на NAS. Дальше тот
  же `index` возвращал те же 6824 байта иконки, **игнорируя новый `link`**, а
  незнакомые `index` отвечали HTTP 404. Похоже, вызов отдаёт из кэша NAS и
  сам по запросу ничего не выкачивает, а кэш наполняется при обновлении
  источника пакетов — но это предположение, а не проверенный факт.
- Отсюда практический вывод: после смены `snapshot` в каталоге надо обновить
  список в Центре пакетов и открыть карточку — до этого галерея не появится.
- `md5` и `size` записи каталога уходят в `SYNO.Core.Package.Installation`
  как `checksum` и `filesize`. Их стоит отдавать, но **причиной «Неверный
  формат файла» они не были**: с правильными суммами обновление падало так
  же. Причину нашёл журнал DSM — у пакета не было ни одной записи
  «successfully updated», только «uninstalled» и «installed», то есть все
  установки шли вручную, а обновление из источника не срабатывало никогда.
- **Ссылка в `link` не должна уводить на другой хост.** Адрес вида
  `github.com/…/releases/download/…` отвечает 302 на
  `release-assets.githubusercontent.com`, и Центр пакетов скачивал что-то,
  что отказывался ставить, — при том что тот же файл, скачанный браузером,
  ставился вручную без нареканий. У SynoCommunity `link` ведёт на их
  собственный сервер. Мы кладём `.spk` на GitHub Pages рядом с каталогом.
- `changelog` в каталоге — **текст**, а не ссылка: что положили, то и
  показывается под «Новые функции версии».

## Установка из каталога требует `checksum` в INFO

Пакет без этого поля Центр пакетов **отказывается ставить из источника**:
код `4521`, в интерфейсе — «Неверный формат файла. Обратитесь к разработчику
пакета». Ни о какой контрольной сумме сообщение не говорит.

`checksum` — это **md5 от `package.tgz`**, лежащего внутри `.spk`. Проверено
на двух чужих пакетах, которые на DSM 7 ставятся из своих источников
штатно:

| пакет | `checksum` в INFO | md5 их `package.tgz` |
|---|---|---|
| Arc Control (apps.xpenology.tech) | `a9e6266865c74e93245f816832fd4da3` | совпадает |
| syno-magnet (SynoCommunity) | `51ff1596198d7b252bfd86e3e757d6f1` | совпадает |

Коварство в том, что **ручная установка этой проверки не делает**. Тот же
файл, поставленный через «Установка вручную», работает годами, и пакет
выглядит исправным — пока кто-нибудь не попробует обновиться из каталога.

Попутно отброшены две правдоподобные, но неверные догадки:

- **Дело не в подписи.** У пакета SynoCommunity есть `syno_signature.asc`, и
  первым подозрением было её отсутствие. Но у Arc Control подписи нет вовсе,
  а он с чужого источника и ставится, и обновляется.
- **Дело не в редиректе и не в `md5`/`size` записи каталога.** Без них ошибка
  та же, а с прямой ссылкой без редиректа — тоже.

Настоящий код ошибки виден только через API: интерфейс показывает
переведённую фразу, а `SYNO.Core.Package.Installation.Download` `check`
возвращает `{"error":{"code":4521}}`. Расшифровка кодов — в
`PkgManApp.js` на самом NAS, функция `getWebAPIErr`.

## Ссылка в каталоге не должна отдаваться сжатой

GitHub Pages **сжимает на лету** то, что отдаёт, и какое-то время `link` в
каталоге указывал именно туда. Замер одного и того же файла:

| откуда | запрос с `Accept-Encoding: gzip` | md5 полученного | что это |
| --- | --- | --- | --- |
| GitHub Pages | 5 249 303 Б, `content-encoding: gzip` | `a409fa72…` | gzip-поток |
| релиз GitHub | 5 335 040 Б, без сжатия | `b27bf5a6…` | POSIX tar |
| `raw.githubusercontent.com` | сжимает | — | gzip-поток |

В каталоге объявлен md5 несжатого файла. Клиенту, который понимает gzip,
Pages физически не может отдать эти байты — то есть **объявленная сумма
описывает не то, что придёт по проводу**. Это дефект независимо от того,
как с ним обходится загрузчик DSM, поэтому `link` указывает на релиз:
файлы релизов GitHub не сжимаются, а редирект на
`release-assets.githubusercontent.com` безвреден.

Проверка встроена в `tools/make-feed.py` (`--verify`, включена в релизном
workflow): каталог скачивает собственную ссылку с `Accept-Encoding: gzip` и
сверяет размер и md5 с тем, что сам же записал. Любой `Content-Encoding` —
отказ собирать каталог.

## Обновление из источника: что проверено и что осталось

Ошибка «Неверный формат файла» (код 4521, `pkgmgr_file_not_package` +
`contact_developer` — расшифровка в `PkgManApp.js`, `getWebAPIErr`)
воспроизводится и через API, без участия человека. Последовательность,
которую делает кнопка «Обновить» (из `PkgManApp.js`):

1. `SYNO.Core.Package.Installation` `upgrade` c `name`, `url`, `checksum`,
   `filesize`, `operation` — возвращает `taskid`;
2. опрос `SYNO.Core.Package.Installation` **`status`** с `task_id` (не
   `Download check` — это разные вещи). Он же показывает `tmp_folder`,
   куда идёт загрузка: `/volume1/@tmp/synopkg/download.XXXXXX`;
3. после `finished` — `SYNO.Core.Package.Installation.Download` `check`;
4. отказ подписи приходит **внутри успешного ответа** как `codesign_error`
   и показывается диалогом «Согласиться» (кроме `4501` — там только «ОК»).
   Наш случай не такой: `check` отвечает `success: false`, код 4521.

Проверено на версии 1.0.4 и **исключено**:

- **Файл.** 20 записей, первая `package.tgz`, `checksum` в INFO равен md5
  `package.tgz`. Тот же файл ставится вручную.
- **Сеть и доставка.** NAS скачал этот же адрес через Download Station —
  5 335 040 из 5 335 040 байт, md5 совпал с каталогом. Файл забран обратно
  с NAS и разобран: валидный POSIX tar.
- **Редирект.** Download Station проходит его без потерь.
- **Соглашение о суммах.** У Arc Control, который на этом NAS стоит из
  чужого источника: `md5` в каталоге — от всего `.spk`, `checksum` в INFO
  — от `package.tgz`. Ровно как у нас.
- **Подпись.** У Arc Control нет `syno_signature.asc` вовсе.
- **Уровень доверия.** `trust_level: 0`, и при нём сторонний arc-control
  на этом NAS стоит.

Осталось непроверенным одно: интерфейс на **исправном** каталоге. Все
прежние попытки пользователя приходились на каталог, который был сломан по
делу — без `checksum` (1.0.0–1.0.2) или со сжимающим хостом (1.0.2–1.0.3).
Повтор через API — неполный: он пропускает `_onCheckEnv` и подготовку тома,
а после первой неудачи подсистема отвечает `4501` на всё подряд, пока не
отпустит.

**Причина пока не названа.** Записывать догадку сюда нельзя — в этом файле
уже был один неверный разбор («limit = -1»).

## macOS кладёт в архив спутники `._*` и сам же их прячет

Касается только сборки на Mac — релизы собирает CI на Linux, поэтому до
пользователей это не дошло. `tar` в macOS (bsdtar) пишет рядом с каждым
файлом AppleDouble-спутник с расширенными атрибутами: `._INFO` рядом с
`INFO`, `._package.tgz` рядом с `package.tgz`. При чтении тот же tar их
скрывает, так что `tar tvf` показывает чистый пакет — а внутри из сорока
записей двадцать мусорные, и **первая запись архива** оказывается
`._package.tgz` там, где разборщик ждёт сам пакет.

Лечится переменной окружения `COPYFILE_DISABLE=1` (GNU tar на Linux её
просто игнорирует, так что сборка одинакова на обеих машинах). Формат
архива задан явно — `--format=ustar`: bsdtar по умолчанию пишет pax, а
pax-заголовок — это ещё одна запись перед настоящей.

Увидеть настоящее содержимое можно чем угодно, кроме системного tar:

```bash
python3 -c "import tarfile;print(tarfile.open('пакет.spk').getnames()[:5])"
```

`tools/build-spk.sh` делает это сам после сборки и падает, если мусор
вернулся или первой записью оказался не `package.tgz`.

## Коды языков DSM

Суффиксы `description_<язык>`, `displayname_<язык>` и файлов мастера
`install_uifile_<язык>` — это коды DSM, а не Telegram:
`enu, cht, chs, krn, ger, fre, ita, spn, jpn, dan, nor, sve, nld, rus, plk,
ptb, ptg, hun, trk, csy`.

Итальянский — **`ita`**. Незнакомый суффикс не считается ошибкой: DSM молча
показывает английский, поэтому опечатку видно только глазами итальянца.
Украинского в списке нет вовсе.

Источник: Synology Package Developer Guide, раздел Optional Fields.
